# Selenium + TestNG in Docker

Two Linux containers run the framework: selenium runs Chrome and ChromeDriver; test-runner runs Maven/Java/TestNG plus a tiny HTTP practice page. Selenium connects to that page at http://test-runner:8080. Java connects to the browser at http://selenium:4444. Inside a container, localhost means that container, so those service names are essential.

## Windows setup
Install Docker Desktop from https://www.docker.com/products/docker-desktop/ and start it. Use Linux containers with the WSL 2 backend enabled. Allocate enough Docker memory for a Chrome container plus the Java runner (about 4 GB or more is practical). Check `docker version` and `docker compose version` in Command Prompt. Host Java, Maven, Chrome, and ChromeDriver are not needed for the full Docker run.

## Run from Command Prompt
Open the extracted folder containing compose.yaml:
```bat
docker compose config
docker compose up --build --abort-on-container-exit --exit-code-from test-runner
```
The command returns the test-runner exit code. The Selenium service waits for its readiness healthcheck before the test-runner starts. Initial downloads require internet and can be large. Docker pulls the official Chrome image pinned to 4.50.0-20261010 and builds a Maven 3.9.9 / Java 21 runner.
After the run:
```bat
docker compose down
```
Alternatively run `run-docker.bat`; it runs the suite, cleans up the containers, and preserves the test exit code. No need to type mvn on Windows.

## Reports
The host reports folder is bind-mounted into the runner, so results persist after containers stop:
- reports/testng: Surefire XML and TestNG reports (including index.html when generated by TestNG).
- reports/screenshots: screenshots on browser-test failure, when a live session exists.
Generated build output stays inside the runner image/container. The reports mount is separate from target, so Maven clean cannot attempt to delete a mounted target root. Reports use fixed suite paths; copy them before another run if you want to retain history.

## Watch Chrome
While tests run, open http://localhost:7900 in your host browser. Connect to noVNC using the image's default password `secret`. Headless is false by default so the remote desktop can show browser activity. Tests may complete quickly. Grid UI: http://localhost:4444. Both ports bind to 127.0.0.1 on the host.

## Test cases
Three independent browser tests: valid login, invalid login, logout. Each gets a fresh RemoteWebDriver session. The demo page uses client-side JavaScript and synthetic credentials; it demonstrates automation, not production authentication security. Three additional configuration/HTTP tests verify settings and that the bundled page is served.

## Configuration
Defaults are in src/test/resources/config.properties. Precedence is Java -D properties, then environment variables, then the properties file.

Setting | Environment variable | Docker value
--- | --- | ---
run.mode | RUN_MODE | remote
remote.url | REMOTE_URL | http://selenium:4444
app.base.url | APP_BASE_URL | http://test-runner:8080
fixture.bind | FIXTURE_BIND | 0.0.0.0
fixture.port | FIXTURE_PORT | 8080
headless | HEADLESS | false
wait.seconds | WAIT_SECONDS | 15 (default)
page.load.seconds | PAGE_LOAD_SECONDS | 30 (default)

Chrome shared memory is 2 GB; max sessions is 1, matching sequential TestNG execution. No parallel test mode is configured. The fixture HTTP port is internal only and not published to the host. Suite XML is testng.xml; pom.xml configures Surefire to execute it.

## Optional local execution
With JDK 21, Maven, and Chrome installed:
```bat
mvn test
mvn -Dheadless=true test
mvn -Dtest=ConfigurationTest test
```
The default run.mode is local; ChromeDriver is obtained by Selenium Manager. Port 8080 must be available. To change it, set both fixture.port and app.base.url. Do not use Docker's test-runner hostname for a local run.

## Rebuild after source changes
Rerun docker compose up --build --abort-on-container-exit --exit-code-from test-runner. The Dockerfile compiles sources with -DskipTests while building; tests run only when the test-runner container starts. Container command does not swallow failures.

## Troubleshooting
- Docker daemon error: start Docker Desktop and ensure Linux containers are selected.
- Ports 4444/7900 busy: change only the host side of compose ports; keep container ports and REMOTE_URL unchanged.
- Practice server bind error: check port 8080 for local runs.
- Grid health timeout: inspect `docker compose logs selenium` and Docker memory limits.
- Browser cannot load page: APP_BASE_URL must be http://test-runner:8080 and FIXTURE_BIND must be 0.0.0.0 inside Docker.
- Image download/build failures: verify registry/Maven Central access and Docker Desktop proxy settings.
- This archive contains configuration and Java source, not Docker images.
